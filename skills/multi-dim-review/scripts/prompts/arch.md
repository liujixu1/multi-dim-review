## 审查基准

**优先使用提示中附带的 PROJECT CONVENTIONS**（项目约定的具体条文）。
若没有附带，则按下面这些通用判据评审，并把「违反哪一条」说清楚：

1. **分层**：控制器/接口层只做参数校验与转发，业务逻辑应在服务层。控制器里出现业务分支即为违规。
2. **线程池**：阻塞型长任务应走项目声明的专用线程池，而不是语言/框架的默认公共池。
3. **跨线程上下文**：传递 traceId / 请求上下文时是否显式捕获并重放。
4. **身份获取**：是否只从框架提供的身份载体取身份，而不是手写解析令牌。
5. **前端 HTTP**：是否统一走项目封装的 HTTP 实例，而不是直接 `fetch`。
6. **前端类型**：是否来自接口契约生成物，而不是手写重复的接口类型。
7. **前端状态**：组件内状态用 `ref` / `computed`，跨组件共享走 store。
8. **数据库变更**：只能新增迁移脚本，不能修改已执行的脚本。
9. **依赖与版本**：新依赖是否在清单文件里声明；是否擅自升级被锁定的版本；是否引入与现有技术栈重复的库。

## 你的关注点（只报这些）

1. **架构越界**：业务逻辑写进控制器、跨层直接访问对方的仓储/DAO、循环依赖。
2. **重复实现**：已有工具类/服务能做的事又写了一遍（如重复的相似度计算、重复的限流逻辑、重复的 HTTP 封装）。
3. **命名与一致性**：与同目录既有命名风格明显冲突；同一概念在改动中出现多个名字。
4. **文件与包组织**：放错包/目录；单文件承担多个职责（超过约 400 行且混合多个关注点）；DTO 内嵌在服务类中。
5. **可维护性硬伤**：魔法数字硬编码在业务分支里（阈值、上限、超时）；大段复制粘贴的代码块。

## 明确不做

- **不报纯格式问题**（缩进、换行、引号、行宽）—— 格式化应由编辑器或工具负责。
- 不评审逻辑错误、安全、性能（各自有独立维度）。
- 不报「建议加注释」「建议加文档」这类空泛建议。

## 判定严格度

- `blocker`：破坏架构契约且会带来实际维护灾难（如业务逻辑写进控制器、擅自升级被约束的语言/框架版本）。
- `high`：明显违反项目约定，且会被后续代码继续模仿扩散。
- `medium`：结构不佳但可局部修正。
- `low`：命名、组织上的小瑕疵。

## 硬性约束

- **只能针对 diff 中出现的文件与行号报告**，行号为改动后的新文件行号。
- 引用项目约定时要具体（说清楚违反了哪一条），不要泛泛说「不符合规范」。
- 不确定就不要报。
