# 项目约定模板

评审标准默认是通用的。把它填成**你项目的实际约定**，评审质量会明显提升。

## 如何使用

1. 复制本文件为你项目里的约定文件；
2. 按下面四块填写真实规则，删掉用不到的；
3. 把内容并入 `scripts/prompts/<维度>.md` 的对应位置（或让调用方在评审请求里附带）。

原则只有一条：**写具体、可判定**。
「代码要整洁」这种无法判定的要求不要写，评审员只会产出噪音。

---

## 一、架构与分层

写清楚「什么东西必须放在哪里」，以及违反时为什么算问题。

```markdown
- 控制器/接口层只做参数校验与转发，业务逻辑必须在服务层。控制器里出现业务分支即为违规。
- 跨层禁止直接访问对方的仓储/DAO，必须走对方公开的服务方法。
- 单文件超过约 400 行且混合多个关注点时应拆分。
- DTO 不得内嵌在服务类里。
```

## 二、安全红线

这一块最值得写，因为通用规则猜不到你的权限模型。

```markdown
- 所有数据访问必须经过 <你的权限过滤层名>。绕过它直接拼查询语句 = blocker。
- 禁止把前端传入的 tenantId / departmentId / roleLevel 当作过滤条件。
- 身份只能从 <你的身份载体名> 获取，禁止手写解析令牌。
- 权限变更后旧令牌必须失效（列出你的实现机制名）。
```

## 三、并发与资源

```markdown
- 阻塞型长任务必须走 <你的专用线程池配置>，禁止用默认公共池。
- 跨线程传递 traceId / MDC 时显式捕获并重放。
- 循环内禁止查库或发 HTTP；全量扫描必须设上限。
```

## 四、技术与版本约束

```markdown
- 运行时版本：<例如 Java 17，不要升到 21>
- 关键框架版本锁定：<例如 Spring Boot 3.5.x，LangChain4j 1.8.0>
- 数据库变更只能新增迁移脚本，禁止修改已执行的脚本。
- 前端 HTTP 统一走 <封装文件路径>，禁止直接 fetch（SSE 例外）。
- 前端类型来自接口契约生成物，禁止手写重复类型。
```

---

## 反例（不要这样写）

```markdown
# 无法判定，只会产生噪音
- 代码要写得优雅
- 注意性能
- 保持一致性
- 建议加注释
```
